# Личный финансовый трекер

Веб-приложение для личного учёта финансов: импорт выписки Т-Банка, автоматическая категоризация
трат, цели с прогнозом накоплений, долги, планирование отпуска по ТК РФ и рейтинг финансовой
ситуации от 0 до 5.

Всё считается на клиенте, статика деплоится на GitHub Pages, данные хранятся в Supabase
(Postgres + Auth + RLS) или локально в браузере, если ключи Supabase не заданы.

---

## Быстрый старт

```bash
npm install
npm run dev
```

Откроется http://localhost:5173. Без переменных окружения приложение работает в **локальном
режиме**: вход не требуется, данные лежат в `localStorage` браузера. Этого достаточно, чтобы
попробовать всё, кроме синхронизации между устройствами.

Чтобы включить облако — создайте `.env.local` по образцу `.env.example`:

```
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon key>
```

## Стек и почему так

| Слой | Выбор | Обоснование |
| --- | --- | --- |
| Frontend | React 18 + Vite + TypeScript | GitHub Pages отдаёт только статику, SPA — единственный вариант |
| Стили | Tailwind CSS 4 | быстрый адаптив без отдельного CSS-слоя |
| Графики | Recharts | декларативные графики на React, хватает для pie/bar/line |
| Состояние | Zustand | один стор, без бойлерплейта Redux |
| БД + Auth | Supabase (Postgres, RLS) | нужен бэкенд без сервера: `supabase-js` ходит в БД прямо из браузера, а RLS-политики гарантируют, что пользователь видит только свои строки. Firebase дал бы то же самое, но данные здесь реляционные (транзакции ↔ категории ↔ цели ↔ долги), и SQL-агрегации по ним удобнее, чем документная модель |
| Хостинг | GitHub Pages | по требованию задачи |
| CI/CD | GitHub Actions | пуш в `main` → сборка → публикация |
| Парсинг выписки | на клиенте (CSV/XLSX) | файл выписки никуда не загружается, обрабатывается в браузере |

Роутинг — `HashRouter`: на GitHub Pages нет серверных редиректов, и прямые ссылки на `/goals`
без хэша отдавали бы 404.

## Возможности

### 1. Онбординг
Аванс и зарплата (суммы и числа выплат), дата трудоустройства, использованные дни отпуска,
текущий остаток на счетах. Анкету можно перепройти в «Настройках».

**Как считается баланс.** Вы называете сумму, которую видите в банке, и она фиксируется на
момент (дата + время). В этой сумме банк уже учёл всю прошлую историю, поэтому импорт выписки
за прошлые периоды баланс **не меняет** — старые операции идут только в статистику и графики.
Баланс двигают лишь операции, произошедшие строго после зафиксированного момента. Сверились с
банком — впишите свежую сумму в «Настройках», момент подставится текущий.

### 2. Импорт выписки Т-Банка
- Форматы: **CSV** (windows-1251 или UTF-8, разделитель `;`, `,` или таб) и **XLSX**.
  PDF не поддерживается — в приложении банка нужно выбрать CSV или Excel.
- Распознаются колонки: `Дата операции`, `Дата платежа`, `Статус`, `Сумма операции`,
  `Валюта операции`, `Сумма платежа`, `Валюта платежа`, `Категория`, `MCC`, `Описание`.
  Сопоставление по синонимам — если банк переименует колонку, парсер это переживёт.
- Операции со статусом `FAILED` / «отклонена» пропускаются.
- Сумма берётся в рублях (`Сумма платежа`), знак определяет доход/расход.
- **Дедупликация**: хэш от даты + суммы + типа + описания. Повторная загрузка того же файла
  не создаёт дублей (проверено: 49 строк → 1 новая, 48 дубликатов). В БД это ещё и
  уникальный индекс `(user_id, dedup_hash)`.
- История импортов с откатом: «Откатить» удаляет все операции конкретной загрузки.

### 3. Автокатегоризация
Приоритет: **MCC-код** → **ключевые слова** в описании и категории банка → фолбэк «Другое».
17 базовых категорий (продукты, кафе, транспорт, подписки, развлечения, здоровье, одежда,
связь, ЖКХ, образование, путешествия, переводы, наличные, комиссии + доходные).
Категории, ключевые слова и цвета редактируются в «Настройках».
Категория, выставленная вручную, помечается `category_manual` и при импорте не перезаписывается.

### 4. Дашборд
Баланс, дни и сумма до ближайшей выплаты, дневной лимит, топ категорий за месяц (диаграмма),
динамика доходов/расходов/остатка по месяцам, краткий срез по целям, долгам и отпуску.

### 5. Цели
Название, нужная сумма, отложено, дедлайн. Считается: сколько откладывать в месяц и с каждой
выплаты, сколько получается по факту, прогноз даты закрытия цели, прогресс-бар. Ручные
пополнения с историей.

### 6. Задолженности
Оба направления («я должен» / «мне должны»), частичные платежи, статусы
`не погашен / частично / погашен`, просрочка по сроку возврата.
Долг можно **привязать к цели** — тогда в цели видно, какая часть суммы закрыта заёмными деньгами.

## Алгоритмы

### Отпускные дни (ТК РФ)

```
28 дней в год  →  2,33 дня за каждый отработанный месяц
право на первый отпуск — через 6 месяцев непрерывной работы (ст. 122 ТК РФ)
```

Отработанные месяцы считаются по правилам исчисления стажа: полные месяцы плюс остаток,
где остаток **≥ 15 календарных дней округляется до полного месяца**, а меньший отбрасывается.

```
накоплено  = месяцы × 2,33
доступно   = накоплено − использовано − запланировано
```

Запланированные периоды выбираются в календаре (первый клик — начало, второй — конец);
если сумма запланированных дней больше доступных, приложение это подсвечивает.

Код: [`src/logic/vacation.ts`](src/logic/vacation.ts).

### Рейтинг финансовой ситуации 0–5

Пять показателей, каждый нормируется в 0..1, затем взвешенная сумма × 5.
Если данных для показателя нет (например, нет целей), он исключается, а веса нормируются
по оставшимся. Если применимых весов меньше половины, рейтинг не показывается — вместо
числа выводится «нет данных».

| Показатель | Вес | 0 баллов | 5 баллов |
| --- | --- | --- | --- |
| Расходы к доходам | **0.30** | откладывается 0% дохода и меньше | откладывается ≥ 25% |
| Прогресс по целям | **0.20** | дедлайн просрочен | темп накоплений ≥ нужного |
| Долговая нагрузка | **0.20** | долг ≥ 6 месячных доходов | долгов нет; каждая просрочка −0.25 |
| Стабильность трат | **0.15** | разброс месячных трат ≥ 60% от среднего | разброс ≤ 20%; крупные разовые траты (>20% дохода) штрафуются по 0.1 |
| Подушка безопасности | **0.15** | остатка нет | остатка хватает на 3 месяца расходов |

Почему такие веса: решающими сделаны две вещи, на которые пользователь влияет напрямую —
сколько он откладывает (0.30) и как идут цели (0.20). Долговая нагрузка не менее важна, но
инерционна — её нельзя починить за месяц, поэтому тоже 0.20. Стабильность и подушка (по 0.15) —
«гигиена»: они корректируют оценку, но не определяют её.

Расчёты идут по среднему за последние **3 месяца** с фактическими данными; если выписки ещё нет,
доход берётся из анкеты. К оценке прилагается текстовое пояснение (что тянет вверх/вниз) и
рекомендации — например, на сколько процентов урезать самую крупную категорию, чтобы закрыть
разрыв по цели.

Код: [`src/logic/rating.ts`](src/logic/rating.ts), [`src/logic/analytics.ts`](src/logic/analytics.ts).

```
src/
  components/     Layout, календарь отпуска, UI-примитивы
  data/           repo.ts (интерфейс), supabaseRepo.ts, localRepo.ts
  lib/            supabase-клиент, форматирование денег и дат
  logic/          parseStatement, categorize, vacation, analytics, rating
  pages/          Login, Onboarding, Dashboard, Import, Transactions, Goals, Debts, Analytics, Settings

supabase/schema.sql   таблицы, индексы, RLS-политики, триггер создания профиля

```

Доступ к данным спрятан за интерфейсом `Repo` с двумя реализациями (Supabase и localStorage),
поэтому приложение работает и без облака.

## Схема БД

`profiles`, `categories`, `imports`, `transactions`, `goals`, `goal_contributions`,
`debts`, `debt_payments`, `vacation_plans`.

Все таблицы с включённым RLS и политикой `auth.uid() = user_id` (у `profiles` — `auth.uid() = id`),
то есть на уровне БД пользователь физически не может прочитать чужие строки.
Триггер `on_auth_user_created` создаёт профиль при регистрации.

Полный SQL: [`supabase/schema.sql`](supabase/schema.sql).

### Данные предыдущей версии

В проекте Supabase остались таблицы `transactions_legacy`, `goals_legacy`, `debts_legacy`,
`vacation_settings_legacy` — это схема прошлого приложения. Ничего не удалялось: 22 операции,
цель и настройки отпуска перенесены в новые таблицы, а старые лежат рядом как резервная копия.
Когда убедитесь, что всё на месте, их можно удалить:

```sql
drop table public.transactions_legacy, public.debts_legacy, public.goals_legacy, public.vacation_settings_legacy;
```

У перенесённых операций `dedup_hash` начинается с `legacy:` — они заводились вручную, а не из
выписки, поэтому в дедупликацию по хэшу выписки не попадают. Если те же операции придут в
CSV из банка, они могут задвоиться — лишнее удаляется на вкладке «Операции».

## Подключение Supabase (5 минут)

1. https://supabase.com → New project (бесплатный тариф).
2. **SQL Editor → New query** → вставить содержимое `supabase/schema.sql` → Run.
3. **Authentication → Providers → Email**: включить. Для личного использования удобно выключить
   «Confirm email», иначе после регистрации нужно подтвердить письмо.
4. **Project Settings → API**: скопировать `Project URL` и `anon public` ключ.
   `anon`-ключ публичный по замыслу — данные защищает RLS, а не секретность ключа.
5. Локально положить их в `.env.local`; для деплоя — в секреты репозитория (ниже).

## Деплой на GitHub Pages

1. Создать репозиторий и запушить код:

```bash
git remote add origin https://github.com/<user>/<repo>.git
git push -u origin main
```

2. **Settings → Pages → Source: GitHub Actions**.
3. **Settings → Secrets and variables → Actions → New repository secret**: добавить
   `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
4. Дальше каждый пуш в `main` собирает и публикует сайт: https://&lt;user&gt;.github.io/&lt;repo&gt;/

Workflow сам подставляет `BASE_PATH=/<имя-репозитория>/` — менять `vite.config.ts` не нужно.
Если секретов нет, сборка всё равно пройдёт, и сайт заработает в локальном режиме.

## Безопасность

- HTTPS обеспечивает GitHub Pages.
- Пароли хранит и хэширует Supabase Auth (bcrypt), приложение их не видит; сессия лежит
  в localStorage в виде JWT и обновляется автоматически.
- Данные закрыты RLS: даже с публичным `anon`-ключом чужие строки не читаются.
- Файл выписки не покидает браузер — парсинг полностью клиентский.
- Ключи не коммитятся: `.env*` в `.gitignore`, в CI они приходят из GitHub Secrets.
